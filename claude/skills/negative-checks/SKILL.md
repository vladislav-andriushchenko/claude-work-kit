# Список негативных проверок по схеме

Механизм подстановки в проекте обычно уже есть — не хватает не движка, а списка. Список выводится из схемы перебором по известным правилам: ровно тот класс работы, который отдаётся агенту.

Вход — готовая JSON Schema или DTO. Выход — таблица параметров, готовая к переносу в провайдер данных.

## Шаг 0. Найти механизм подстановки, а не изобретать его

Прежде чем перебирать нарушения, найти в проекте то, чем поле удаляют и подменяют по пути внутри тела запроса. Искать по тестовому дереву: хелперы и билдеры с методами вида «собрать без поля», «собрать с полем», работа с JSON-путём, `JsonPath`, `ObjectNode`, `jsonPatch`.

- **Нашёлся** — брать его имена в колонку «чем делается» и записать их в `~/.claude/rules/project.md`, чтобы больше не искать.
- **Не нашёлся** — так и сказать одной строкой и выдать таблицу без этой колонки. Список путей и нарушений полезен сам по себе; выдуманное имя хелпера — нет.

Своего механизма не писать. Это отдельная задача и отдельное решение владельца кода.

## Что перебрать по каждому полю

| Нарушение | Когда применимо |
|---|---|
| Поле отсутствует | поле в `required` |
| Тип подменён | всегда |
| Формат нарушен | у поля есть `format` |
| Значение вне границ | есть `minimum`/`maximum`/`minLength`/`maxLength` |
| Значение вне перечисления | есть `enum` |
| Пустая строка и пробелы | строковые поля |
| Лишнее поле | схема с `additionalProperties: false` |

Вложенные объекты обходить по тем же правилам, путь строить полностью. Для массивов отдельно: пустой массив, элемент неверного типа, нарушение `minItems`/`maxItems`.

## Ожидаемый результат каждой проверки

По каждой строке указать ожидаемый код ответа и код ошибки.

**Брать их из кода сервиса.** Не из соседнего теста, не по аналогии, не по здравому смыслу. Один и тот же класс нарушения в разных методах отдаёт разные коды, и захардкоженный ожидаемый статус — известный источник ложнозелёных тестов.

**Если код в сервисе найти не удалось — так и написать в строке: `код не найден`.** Не подставлять 400 по умолчанию. Строка с честным пробелом полезна, строка с выдуманным кодом вредна: она пройдёт ревью и будет годами охранять неверное поведение.

## Формат вывода

Таблица: путь к полю, вид нарушения, подставляемое значение, ожидаемый код, ожидаемый код ошибки, чем делается (если механизм найден). Плюс отдельным списком — поля, по которым чего-то не хватило в схеме или в коде сервиса.

## Чего не делать

**Не писать сами тесты.** Только список параметров.

**Не выкидывать скучные комбинации ради краткости.** Объём здесь и есть ценность: перебор по правилам — это то, что человек делает медленно и с пропусками.

**Не изобретать проверки, которых схема не обосновывает.** Если ограничения нет в схеме — проверять нечего, а придуманное ограничение даст падение на валидных данных.

# Схема из спецификации

Вход — кусок Swagger или описание ответа, вставленный в запрос текстом. Выход — файл схемы и одна строка о том, чем его подключить. Ничего больше.

## Что сделать

1. Разобрать вставленную спецификацию: поля, типы, обязательность, форматы, перечисления, вложенные объекты и массивы.
2. Собрать JSON Schema по правилам ниже.
3. Записать файл в `src/test/resources/schemas/`. Имя — по методу API, в стиле соседних файлов в этом каталоге; посмотреть их перед тем, как придумывать своё.
4. Вывести одну строку: какой шаг ассерта подключает эту схему. Взять из существующего кода, не сочинять.

## Правила схемы

**`additionalProperties: false` обязательно, на каждом уровне вложенности.** Без этого схема пропускает лишние поля, то есть ловит один класс нарушений из двух. Это не стилистика: сервис, добавивший поле молча, должен ронять тест.

**`required` полный.** Перечислить все поля, которые спецификация объявляет обязательными. Если в спеке обязательность не указана явно — не угадывать, а спросить.

**Форматы переносить, не выдумывать.** `uuid`, `date-time`, `email`, `uri` ставятся тогда и только тогда, когда они есть в исходной спецификации. Поле с именем `id` не обязано быть `uuid`, а `created` не обязано быть `date-time` — бывает строка в своём формате.

**Перечисления переносить целиком.** Неполный `enum` даёт ложное падение на валидном ответе.

**Числа.** Различать `integer` и `number`. Границы (`minimum`, `maximum`) переносить, если они в спеке есть.

## Чего не делать

**Не генерировать тест.** Только схему. Тест пишется отдельно и по месту, с нужными аннотациями и в нужной ветке дерева.

**Не додумывать поля, которых нет во вставленном куске.** Спека могла быть скопирована частично. Лучше сказать «в этом фрагменте нет описания вложенного объекта X» и остановиться, чем собрать правдоподобную схему, которая разойдётся с сервисом.

**Не переиспользовать схему соседнего метода «потому что похоже».** Похожие ответы у разных методов расходятся в мелочах, и именно эти мелочи схема и должна ловить.

## Что сказать в конце

Одной строкой: путь к созданному файлу, число обязательных полей, и явно — какие поля спецификации остались неясными, если такие были. Список неясностей важнее самой схемы: он показывает, где схема слабее, чем выглядит.

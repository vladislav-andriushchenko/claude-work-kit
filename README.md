# claude-work-kit

Набор для Claude Code на рабочей машине: два правила, четыре скилла, два хука.
Ставится в `~/.claude`, под конкретный проект разворачивается сам.

Внутри нет ни одного имени, модуля или конвенции конкретного проекта — и это не
случайность, а устройство набора. Единственный файл, который зависит от проекта,
собирается на месте по коду репозитория и остаётся на машине.

## Установка: сказать это агенту

На рабочей машине открыть Claude Code в корне проекта и дать одну команду:

```
Поставь набор https://github.com/vladislav-andriushchenko/claude-work-kit по инструкции в его AGENT-SETUP.md, потом настройся под этот проект.
```

Дальше агент делает всё сам: раскладывает файлы в `~/.claude`, включает хуки в
`settings.json`, прогоняет их селф-тесты и запускает скилл `kit-bootstrap`, который
читает сборку, тестовое дерево и конфиг CI и собирает из них `rules/project.md`.

Проверить, что вышло: перезапустить Claude Code (правила и скиллы читаются на
старте) и спросить «какие правила проекта у тебя сейчас».

Руками, без агента:

```powershell
powershell -ExecutionPolicy Bypass -File .\install.ps1
```

Установщик ничего не перезаписывает молча: отличающийся файл кладётся рядом как
`.new`. `settings.json` он не трогает вообще — вставить туда содержимое
`settings-hooks-snippet.json`.

**Что нужно:** Claude Code и `bash` (на Windows — Git Bash, хуки на нём).
Правила и скиллы работают и без bash, хуки — нет.

## Что внутри

```
claude/rules/agent-hygiene.md      четыре правила про то, как агент врёт о результате
claude/rules/data-boundary.md      пять правил про то, что не уходит с машины наружу
claude/rules/incident-log.md       как вести журнал поломок, допущений и правил
claude/incidents.md                пустая заготовка самого журнала
claude/skills/kit-bootstrap/       собрать rules/project.md под конкретный проект
claude/skills/schema-from-spec/    JSON Schema из куска Swagger
claude/skills/negative-checks/     список негативных проверок по схеме
claude/skills/bench-the-fix/       сделать из коммита-починки постоянную проверку
claude/hooks/untracked-tests.sh    неотслеживаемые файлы в тестовом дереве
claude/hooks/false-green.sh        подавление падений в индексе
```

Правила лежат в `~/.claude/rules/` и подхватываются сами, вызывать их не надо.
Это и есть причина, по которой конвенции живут правилом, а не скиллом: скилл,
который вызывают руками, забудется в первый же горячий день, а правило действует
всегда.

Рабочих скиллов ровно два — схема из спецификации и список негативных проверок.
Оба выбраны по одному признаку: **польза не зависит от того, окажется агент умным
или нет.** Это перебор по известным правилам с известным целевым форматом. Всё,
что требует суждения, здесь отсутствует намеренно.

Два других обслуживают сам набор: `kit-bootstrap` настраивает его под проект один
раз, `bench-the-fix` отвечает на вопрос, есть ли от него польза. Ни один из них не
пишет тесты и в ежедневный поток не входит.

## Почему в наборе есть пустой файл

`agent-hygiene.md` требует: правило живёт в файле, а не в переписке. Человек
объяснил одно и то же второй раз — значит оно нигде не записано, оформлять надо
сразу. Требование верное, но само по себе оно бесполезно: агенту сказано «пиши»,
а куда — не сказано. Он либо промолчит, либо положит запись туда, где её никто
больше не найдёт.

`incidents.md` — этот адресат. Три таблицы: поломки, которые уже случались,
допущения, на которых агент себя поймал, и правила, родившиеся из коррекций.
Первая экономит время на повторной диагностике: правило велит открыть журнал до
любых команд, когда человек говорит «опять». Вторая ловит самую дорогую ошибку
агента — догадку, поданную как факт, на которой потом строится всё остальное.

Третья таблица живёт по двум порогам. Больше двадцати строк — свалка, которую
перестали читать. Пусто через месяц — механизм мёртв, коррекции уходят в
переписку и теряются. Ревизия раз в месяц: правила должны не только прибывать.

Установщик кладёт заготовку только если файла нет. Заполненный журнал он не
трогает — заготовка ляжет рядом как `.new`.

## Почему правила проекта не лежат в репозитории

`rules/project.md` — единственный файл, зависящий от проекта, и одновременно
единственный, где есть настоящие имена модулей, классов и аннотаций. Он собирается
на месте скиллом `kit-bootstrap` и никуда не уезжает.

Главное правило скилла — **три исхода на каждый пункт**: выведено из кода,
получено ответом человека, не установлено. Четвёртого исхода нет. Правдоподобная
конвенция, выведенная из общих соображений, хуже отсутствующей: отсутствующую
человек допишет, а правдоподобную примет на веру и будет по ней жить.

Отсюда же два приёма внутри скилла. Выборка тестовых файлов берётся **из разных
областей дерева, а не первые пятнадцать по алфавиту**: соседние по алфавиту файлы
обычно писал один человек за один заход, и их общая черта конвенцией проекта не
является. Признак попадает в правила, если встречается не меньше чем в двух третях
выборки; меньше — записывается как разнобой, а не как правило.

Если проект запрещает project-конфиги в репозитории, это закрывается один раз и
механически:

```bash
git config --global core.excludesFile ~/.gitignore_global
```

```bash
echo ".claude/" >> ~/.gitignore_global
```

## Замер: годится ли то, что выходит из скилла

Судьба скилла решается журналом, а не ощущением. Одна строка на запуск, четыре
поля, все механические:

```
дата ; скилл ; артефактов на выходе ; правил / принял как есть / выбросил
```

Пятое поле дописывается позже и только по факту: `поймал дефект`.

Порог отказа грубый и назначен заранее: восемь «выбросил» из десяти подряд — скилл
не работает, переписывать или удалять.

Чего в журнале **нет намеренно** — сэкономленного времени. В одиночку, без
контрольной группы, экономию времени доказать нельзя: выборка мала, набор задач
после появления скилла смещается сам, а за полгода меняются и модель, и знание
собственного кода. Журнал отвечает на вопрос «годится ли то, что выходит из
скилла», и только на него.

## Хуки: что они ловят и почему их два

**`untracked-tests.sh`** — неотслеживаемые файлы в тестовом дереве. Написанный и
не закоммиченный тест не существует ни в одной ветке и умирает от одного
`git clean`. Гейт на завершение хода, в сомнении пропускает.

**`false-green.sh`** — появление в индексе `ignoreFailures`, `continueOnError`,
`allow_failure` и `|| true` в конфигурации CI. Пайплайн, который зелёный при
упавших тестах, — самый дорогой вид молчаливого фолбэка. Гейт на коммит, в
сомнении запрещает.

Разница в направлении сомнения намеренная: пропущенный незакоммиченный файл стоит
минуты, пропущенное подавление падений — месяцев ложной уверенности.

У обоих есть свой прогон:

```bash
bash claude/hooks/untracked-tests.sh --selftest
```

```bash
bash claude/hooks/false-green.sh --selftest
```

## Проверено

Оба хука прогнаны на настоящем репозитории. Каждый дефект ниже был виден **только
прогоном**: код при чтении выглядел рабочим.

**Первый круг.** Хук неотслеживаемых файлов не сработал там, где должен был:
`git status --porcelain` схлопывает неотслеживаемый каталог в одну строку `?? src/`,
и фильтр мимо неё проходил. Починено флагом `-uall`.

**Второй круг, у хука ложно-зелёного три дефекта.**

- **Блокировал любой вызов Bash, а не коммит.** Матчер в `settings.json` умеет
  только имя инструмента, а хук команду не читал: на `ls -la` отвечал тем же
  отказом. Хуже, отказ прилетал и на `git restore --staged`, то есть выхода из
  блокировки не оставалось. Починено разбором команды из stdin.
- **Совет в сообщении не работал.** `--no-verify` — флаг git-хуков, на
  PreToolUse-хук он не действует.
- **Ложное срабатывание на `|| true`.** В обычном шелле это норма. Теперь
  `|| true` подозрителен только в конфигурации и скриптах CI.

Отсюда уточнение: **в сомнении запрещает находка, а не сантехника.** Не удалось
понять, что за команда, — это не сомнение, а незнание, и тогда хук молчит. Гейт,
который при незнании блокирует всё, запирает агента без выхода.

**Третий круг: починенный хук отдан на ревью чужой модели.** Автором кода был
агент, а ревьюер берётся всегда другого производителя, чем автор. Требование по
каждому замечанию — конкретный сценарий отказа. Три находки, две настоящие.

- **Отделение коммита работало по подстроке.** Шаблон ловил `git log --grep=commit`
  и `git diff --stat # что коммитить`, то есть половина починки первого круга
  оставалась недоделанной. Заменено на разбор `commit` как подкоманды.
- **Перенос строки обходил гейт.** Подавление, разорванное обратным слешем на две
  строки, — то же подавление, но однострочный поиск его не видит.
- **Отклонено:** «пропуск при медленном stdin». Сценарий не строится — ревьюер
  спутал stdin хука со стандартным вводом самой команды.

Поучительная деталь: **оба сценария ревьюера по первой находке при прогоне не
воспроизвелись** — его примеры содержали кавычки, а на них старый шаблон как раз
спотыкался. Находка оказалась настоящей, обоснование при ней — нет. Ровно ради
этого замечание проверяется прогоном, а не чтением.

**Четвёртый круг, 29.08: хук неотслеживаемых файлов был пропущен мимо ревью и
оказался сломан ровно там, где его не проверяли.** Разбор командой `git status
--porcelain` через поле `awk` молча терял всё, что git цитирует, а цитирует он
пути с пробелами и не-ASCII. Три сценария, все воспроизведены:

- `tests/my folder/run test.py` — не найден, гейт открыт, `exit 0`;
- `tests/каталог/test.py` — не найден, git эскейпит кириллицу восьмеричными кодами;
- `src/test/cats with space/a.txt` — найден, но в отчёте напечатано `"src/test/cats`,
  то есть путь, по которому файл не открыть.

Селф-тест при этом говорил `selftest ok`: он строил только пути без пробелов.
Зелёный прогон при сломанной функции — тот самый ложный сигнал, ради которого
второй хук вообще написан.

Починено переходом на `git ls-files --others --exclude-standard -z`: пути
приходят как есть, по одному на запись. Заодно убран из шаблона голый `test/` —
так называют и каталоги с данными, а блокировать их значит нарушать собственное
правило «в сомнении пропускать». Селф-тест вырос с пяти проверок до десяти и
теперь включает пробел, кириллицу и `test/artifacts/`.

Вывод не про парсинг. Первый хук прошёл ревью чужой модели и стал крепче,
второй не прошёл только потому, что про него не вспомнили, — и сломан оказался
именно он.

**Пятый круг, тем же днём: хук ложно-зелёного отдан второму ревьюеру.** Первый
круг ревью делал `deepseek-chat`, этот — `glm-5.2`, то есть третий производитель
после автора. Шесть находок, пять воспроизвелись на Windows, одна не строится на
этой файловой системе. Гейт при этом считался проверенным: он уже проходил ревью
и селф-тест из девяти случаев.

Четыре из них открывали гейт молча:

- `git -c user.name="Jane Doe" commit` не опознавался как коммит: шаблон резал
  значение флага по первому пробелу. Коммит с многословным именем автора проходил
  мимо гейта целиком;
- `git --no-pager commit` и `git --git-dir=… commit` — тоже: допускался только
  флаг `-c`;
- `continue-on-error: true` не ловился. В шаблоне стояла камель-форма
  `continueOnError` из Azure, а GitHub Actions пишет через дефис — то есть самый
  распространённый CI в мире гейт не видел;
- `Jenkinsfile` не считался конфигурацией CI, и `|| true` в нём не проверялся.

Две — ложные срабатывания. `echo git commit` принималось за коммит, потому что
слева у шаблона не было границы команды. И файл, **названный**
`ignoreFailures=true.txt`, блокировался при пустом содержимом: заголовок диффа
`+++ b/<путь>` начинается с плюса и попадал в поиск наравне с добавленными
строками.

Не воспроизвелось: имя файла с переводом строки. На Windows такой файл не
создаётся. Разбор всё равно переведён на `-z`, потому что тем же дефектом
цитирования терялись пути с пробелами, а они создаются прекрасно.

Селф-тест вырос с девяти проверок до восемнадцати. Главное здесь не список
починок: **хук считался проверенным.** Он прошёл ревью, имел селф-тест и три
круга разбора. Второй ревьюер другого производителя нашёл в нём шесть дефектов
за три минуты.

**Шестой круг: второй ревьюер прошёлся и по хуку неотслеживаемых файлов.** Тот
уже был починен по итогам первого круга, `glm-5.2` нашёл ещё четыре, три
воспроизвелись.

- **`spec/` блокировал спецификации.** `spec/openapi.yaml` — не тест, а описание
  API, и хук на нём выходил с кодом 2. Прямое нарушение собственного правила «в
  сомнении пропускать». Каталог убран из шаблона вместе с уже убранным `test/`:
  оба имени носят не только тесты.
- **Селф-тест не охранял альтернативы шаблона.** Проверялись только `src/test` и
  `tests`. Ревьюер доказал это мутацией: урезал шаблон до двух корней, и
  селф-тест остался зелёным, хотя `src/it` и `__tests__` перестали ловиться.
  Теперь по случаю на каждую альтернативу, и та же мутация валит прогон.
- **Вложенный репозиторий давал ложную тревогу.** `git ls-files --others`
  схлопывает его в одну запись `tests/`, хук её ловил и сообщал, что файлы
  «потеряются от одного git clean». Проверка: `git clean -fdn` не показывает
  ничего, внутрь вложенного репозитория clean не заходит. Записи с косой чертой
  на конце теперь отбрасываются.

Не воспроизвелось то же, что и в пятом круге: имя файла с переводом строки, на
Windows такой файл не создаётся.

Отдельно ревьюер перечислил шесть проверенных случаев, где дефекта нет:
поведение вне репозитория, пустой вывод, `CLAUDE_PROJECT_DIR` с пробелом,
игнорируемые файлы, зарегистрированный подмодуль и вложенный репозиторий под
не-тестовым путём. Такой список стоит отдельно: он показывает, где гейт
проверен, а не только где починен.

## Чего здесь нет и не будет

| Не ставить | Почему |
|---|---|
| Скилл триажа прогонов | Самый популярный скилл в нише. Бесполезен там, где прогоны стабильны: без двух-трёх десятков падений в месяц мерить нечего |
| Матрица трассируемости | Умирает через месяц в любом проекте, где её не ведут люди |
| Тест-планировщик | Нужен там, где есть формальные планы. Где их нет — это генератор бумаги |
| Генерация тестов целиком | Воюет с архитектурой, если слои выстроены осознанно |
| MCP и браузерный мост | Всё перечисленное работает на вставленном тексте и локальном git |

Набор короткий не из аскетизма: **много скиллов замедляют агента** — он
просматривает всё, что у него есть, на каждый запрос.

## Практики, которые не файлы

**Тяжёлый шаг — новое окно.** Качество ответов заметно падает после 40-50%
заполнения контекста. Ощущение «агент поглупел» почти всегда означает
переполненное окно, а не плохую модель.

**Хендофф перед закрытием тяжёлого окна.** Десяток строк, чтобы следующее окно
подхватило работу, а не собирало контекст заново.

**Коммит после каждого закрытого куска.** Точка отката важнее аккуратной истории.

**Скиллы читаются на старте сессии.** Положил файл — перезапусти Claude Code.

**Следи за вложенностью каталога скилла.** Должно быть `skills/имя/SKILL.md`.
Лишний уровень `skills/имя/имя/SKILL.md` рождается при распаковке архива, и скилл
молча не работает — без ошибки, просто не срабатывает.

**Чужой скилл — сначала аудит, потом установка.** Проверить, нет ли чтения `.env`,
обращений на внешние адреса и вшитых ключей. На рабочей машине это условие, а не
паранойя. Этот набор — не исключение: девять файлов, читаются за десять минут.

## Стенд рядом

Правила отвечают на вопрос «как надо», но не на вопрос «стало ли лучше». На второй
отвечает [bench-your-bugs](https://github.com/vladislav-andriushchenko/bench-your-bugs):
он делает из коммита-починки постоянную проверку и показывает, ловит ли обвязка
настоящие дефекты этого проекта. Скилл `bench-the-fix` — шов между ними.

Репозитории намеренно раздельные. Стенд работает у любого, у кого есть
коммиты-починки, независимо от языка и инструмента. Набор работает только у того,
у кого Claude Code. Слияние сузило бы более общий инструмент до аудитории менее
общего.
